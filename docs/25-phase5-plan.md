# 25 — Phase 5 Plan

## Objective

Phase 5 turns the Phase 4 synthetic-data release into a production-ready platform, then extends it with selected integrations and advanced analytics. Work is sequenced so governance and security gates come before any real staff data or external system connection.

## Guiding constraints

- Do not process real staff data until every go/no-go criterion in doc 24 is met.
- Preserve the modular monolith boundary: new capabilities get API services, shared DTOs, permissions, audits and tests before UI breadth.
- Every workflow must remain scoped, auditable and demonstrable with synthetic data.
- Privacy-sensitive integrations require policy approval before implementation.

## Delivered in this increment

- **Production foundations:** config validation, production guardrails, demo-seed lock, backup checksums, dependency/filesystem scan workflow and Dependabot.
- **MFA:** TOTP enrolment, six-digit verification, one-time recovery codes, login challenge flow, rate limits, audit events, privileged-route enforcement and web enrolment UI.
- **Transport and operations:** HTTPS/HSTS reverse-proxy template, liveness/readiness endpoints and structured JSON API logs.
- **Advanced analytics starter:** per-user saved report filters with create, apply and delete flows.

Still open before real data: secret-manager injection and key rotation, encrypted object storage, advisory remediation and blocking scans, metrics/alerts, certificate lifecycle operations, institutional privacy approvals and the remaining extension workstreams below.

## Workstream 1 — Production readiness gate

Priority: mandatory before real data.

### Scope

1. **MFA for privileged accounts**
   - Add TOTP enrolment, verification, recovery codes and per-user enforcement.
   - Require MFA for roles with `user.manage`, `role.manage`, `audit.view`, `access.delegate` or `report.export`.
   - Add login challenge endpoints, rate limits, audit events and API tests.
   - Keep recovery-code use audited and one-time.

2. **HTTPS and proxy hardening**
   - Add a reverse proxy configuration that terminates TLS, redirects HTTP and sets HSTS.
   - Confirm secure refresh cookies, `__Host-` prefix and `SameSite` policy.
   - Document certificate renewal and trusted proxy settings.

3. **Secret management**
   - Replace deployed `.env` usage with runtime injection from the institution's secret manager.
   - Add JWT key rotation with key IDs and overlapping validity windows.
   - Remove plaintext secrets from local test workflows where feasible.

4. **Protected object storage**
   - Introduce a storage adapter with a local driver for development and an encrypted object-storage driver for production.
   - Add least-privilege credentials, encryption at rest, versioning, lifecycle rules and malware scanning.
   - Add retention-aware purge jobs for archived documents.

5. **Security automation remediation**
   - Upgrade Zod with schema migration tests.
   - Upgrade or replace Prisma tooling affected by transitive advisories.
   - Make dependency and Trivy scans blocking once high/critical findings are cleared.

6. **Observability**
   - Add structured logs, liveness/readiness endpoints, metrics and alert rules.
   - Alert on login throttling, privilege assignment, export spikes, failed restores and storage capacity.

### Acceptance criteria

- Privileged login without MFA is impossible and tested.
- No plaintext secret is required in the deployed environment.
- HTTPS is enforced and secure cookies are verified in a browser.
- Uploads are encrypted and inaccessible without an authorized API request.
- Scanning workflows are blocking with no high/critical findings.
- Restore drill passes with checksum verification and recorded evidence.

## Workstream 2 — Notification channels

Priority: high after production gate.

### Scope

- Email notification channel with templates, opt-out rules and delivery status.
- Optional SMS/push channel only after consent and cost review.
- Retry, bounce handling and notification audit trail.
- User preference page for channel selection.

### Acceptance criteria

- Templates are reviewed and contain no sensitive values.
- Failed deliveries are visible to administrators and do not leak personal data.
- Employees can opt out where policy permits.

## Workstream 3 — Payroll and compensation

Priority: medium, policy-dependent.

### Scope

- Salary scale, pay grade, allowance and payslip-record models.
- Compensation change workflow with effective dates and approval.
- Payroll export with strict separation from ordinary HR roles.
- Reconciliation report and audit trail.

### Acceptance criteria

- Compensation fields are excluded from standard employee DTOs.
- Dedicated permissions and row scope are tested.
- Payroll exports are audited and cannot be generated by departmental managers.

## Workstream 4 — SSO and identity integration

Priority: medium.

### Scope

- OIDC/SAML integration with the institutional identity provider.
- Just-in-time user provisioning and role mapping rules.
- MFA assertion handling and break-glass account policy.
- Deprovisioning event handling.

### Acceptance criteria

- Role mapping is deterministic and test-covered.
- Deprovisioned identities lose sessions immediately.
- At least one break-glass admin remains recoverable and audited.

## Workstream 5 — Attendance and biometrics

Priority: low; privacy gate first.

### Scope

- DPIA and institutional policy approval before any code.
- Device integration only after data minimization and retention decisions.
- Attendance exceptions workflow with manager review.
- Biometric templates must not be stored by this system unless explicitly approved.

### Acceptance criteria

- No raw biometric data is persisted.
- Device data contains only approved fields.
- Employees can review and contest attendance records.

## Workstream 6 — Advanced analytics

Priority: low.

### Scope

- Workforce forecasting with documented assumptions.
- Succession planning using approved talent-review fields.
- Policy assistant with retrieval limited to published institutional documents.
- Saved report filters (delivered) and scheduled delivery (open).

### Acceptance criteria

- Forecasts are clearly labelled as estimates.
- Succession data has tighter permissions than ordinary HR data.
- Policy assistant answers cite source documents and never invent policy.
- Scheduled exports obey the same scope and export permissions as manual reports.

## Suggested sequence

| Milestone | Work | Exit evidence |
| --- | --- | --- |
| P5-M1 | Config, backup integrity, scan remediation | Doc 24 checklist updated; audit clean |
| P5-M2 | MFA and HTTPS | Privileged MFA tests; TLS walkthrough |
| P5-M3 | Secrets and storage | Secret-injection runbook; storage adapter tests |
| P5-M4 | Observability and go-live readiness | Alerts, dashboards, restore drill |
| P5-M5 | Notification channels | Template and delivery tests |
| P5-M6 | Payroll or SSO, whichever policy approves first | Workflow tests and demo |
| P5-M7 | Advanced analytics and optional attendance | Scope/privacy review and demo |

## Decisions needed from the institution

1. Approved identity provider and SSO protocol.
2. Approved secret manager and object-storage platform.
3. Privacy owner and DPIA sign-off authority.
4. Retention periods for employee records, documents, audit events and backups.
5. Whether payroll, attendance or notifications deliver the most value first.
6. Which roles are treated as privileged for mandatory MFA.

## Definition of done for Phase 5

- All P5-M1 to P5-M4 gates pass and are signed off.
- At least one major extension workflow is implemented, tested and demonstrated with synthetic data.
- Documentation includes updated architecture, security review, runbook, user guide and backlog.
- Full lint, typecheck, build, API test and restore-drill evidence are recorded.
